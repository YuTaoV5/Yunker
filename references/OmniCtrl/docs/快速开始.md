
本节将从一个普通 MCU 工程开始，完成 OmniCtrl 的首次接入，并最终通过 OmniCtrl Studio 创建并下发第一张控制拓扑。

完成本教程后，你将跑通下面这条完整流程：

```text
加入 OmniCtrl
     ↓
配置工程能力
     ↓
生成配置代码
     ↓
完成 MCU 端接入
     ↓
编译并烧录
     ↓
使用 OmniCtrl Studio 搭建控制拓扑
     ↓
生成控制数据
     ↓
下发至 MCU
     ↓
重新启动并运行
```

---

# 1. 将 OmniCtrl 加入工程

OmniCtrl MCU 端代码位于：

```text
OmniCtrl/firmware/
```

可以直接将整个目录加入现有 MCU 工程。

```text
Your_Project/
├── APP/
├── BSP/
├── ...
└── OmniCtrl/
    └── firmware/
```

也可以像本仓库中的 DC Motor Driver 示例一样，直接引用仓库中的 OmniCtrl 源码，而不复制一份新的代码。

OmniCtrl 内部使用相对路径引用自身文件，因此不需要针对不同 MCU 修改内部引用关系。

工程至少需要能够找到：

```text
OmniCtrl/firmware/
OmniCtrl/firmware/bases/Inc/
```

以便应用程序包含：

```c
#include "control_core.h"
#include "control_comm.h"
```

> 📖 如果需要了解完整的工程组织方式，可以参考  
> [项目详细说明](./详细说明.md)

---

# 2. 配置当前工程

打开：

```text
OmniCtrl/firmware/omni_manifest.json
```

该文件用于描述当前项目使用的算子模块和外部控制量，同时作为 MCU 端配置生成与 Studio 界面生成的共同配置来源。

假设目标工程中存在：
```c
float input;
float output;
```

并定义在：
```text
app_control.h
```

那么可以将它们加入配置，例如：
```json
"params_include": [
    "app_control.h"
],

"Params": [
    {
        "Name": "Input",
        "Type": "CTRL_PARAM_SIGNAL_T",
        "Ptr": "input"
    }
],

"OutputParams": [
    {
        "Name": "Output",
        "Ptr": "output"
    }
]
```
其中：
- `Name` 上位机显示的变量名称；
- `Type` 变量的数据类型（默认 SIGNAL 为 float 类型，out 固定为信号类型）；
- `Ptr` 变量的指针，该字段会在 MCU 端完全展开用于变量注册；

> ⚠️ **类型必须与实际变量保持一致。**  
> 当前 `CTRL_PARAM_SIGNAL_T` 按 `float` 类型处理，请勿直接绑定 `int`、`uint32_t` 等其他类型变量，否则可能造成错误访问甚至系统异常。

---

# 3. 生成 MCU 配置代码

完成 `omni_manifest.json` 后运行：
```bash
python OmniCtrl/firmware/config_c.py
```

脚本会读取当前 Manifest，并自动生成：
```text
OmniCtrl/firmware/bases/Src/control_config.c
```
该文件负责完成当前工程所使用的算子和参数注册。

正常情况下可以看到类似输出：
```text
Reading configuration from .../omni_manifest.json...
Generating C code...
Successfully generated .../control_config.c
```

> `control_config.c` 为自动生成文件，不建议手动修改。  
> 当 Manifest 发生变化时，重新运行 `config_c.py` 即可。

针对上述配置的最终效果如下：
```C
#include "app_control.h"

CtrlModule_Registry_Param("Input", CTRL_PARAM_SIGNAL_T, &(input), 0);
CtrlModule_Registry_Param("Output", CTRL_PARAM_SIGNAL_T, &(output), 0);
CtrlModule_Registry_Param("Output", CTRL_PARAM_SIGNAL_T, &(output), 1);
```
应需要确保 MCU 工程的 Include Path 中能够找到该头文件。

# 4. 接入 OmniCtrl

完成配置后，需要在应用程序初始化阶段完成 OmniCtrl 的接入。

DC Motor Driver 中的完整参考代码位于：
```text
examples/DC_Motor_Driver/firmware/APP/Src/app_ctrl.c
```

其核心结构如下：
```c
#include "control_core.h"
#include "control_comm.h"

void APP_Ctrl_Init(void)
{
    /* 注册控制数据下载模式 */
    Control_Comm_Register_Bootloader(Boot_Process);  // 用于进入引导模式

    ...

    /* 将已经保存的控制拓扑读取到 graph */
    Flash_Read(GRAPH_FLASH_ADDRESS,
               graph,
               CONTROL_COMM_GRAPH_SIZE);

    /* 初始化 OmniCtrl */
    ControlCore_Init();
}
```
这里主要完成三件事：
1. 提供控制数据的下载方式；
2. 将之前保存的控制拓扑加载到 `graph`；
3. 调用 `ControlCore_Init()` 完成初始化。

其中 `Boot_Process()`、Flash 读取以及具体通信方式都由目标工程自行实现，并不要求必须使用 UART 或 Flash，例如：
```text
UART + Flash
USB  + Flash
CAN  + EEPROM
RS485 + 外部存储器
```
都可以根据实际硬件选择。

`Boot_Process()` 用于实现控制拓扑的接收与保存。当 OmniCtrl 检测到下载模式标志后，会在初始化过程中进入该函数。具体通信方式和存储方式由目标工程自行实现。

> 💡 **关于下载模式** ：OmniCtrl 通过 `control_into_bootloader` 判断是否进入下载模式，并在 `ControlCore_Init()` 中调用已注册的 `Boot_Process()`。

> 上面的 `Flash_Read()` 仅用于说明数据加载过程，具体函数参数请根据自己的存储驱动实现。

---

# 5. 周期执行 OmniCtrl

初始化完成后，需要在合适的位置周期调用：
```c
ControlCore_Update();
```

例如：
```c
void Control_Loop(void)
{
    ControlCore_Update();
}
```
可以将其放在：
- 定时器任务；
- RTOS 周期任务；
- 已有的控制周期函数；
等适合当前控制系统的位置。

如果需要使用 OmniCtrl 的输出结果，也可以通过：
```c
ctrl_output_signal[]
```
获取。

DC Motor Driver 中的实际使用方式为：
```c
void APP_Ctrl_Process(void)
{
    Data_Update(input);     // 更新数据

    ControlCore_Update();   // 执行计算

    Data_process(ctrl_output_signal[0]);  // 根据计算结果响应
}
```
至此，OmniCtrl MCU 端的基本接入已经完成。

---

# 6. 编译并烧录

将 OmniCtrl 相关源码加入工程后，重新编译项目，主要确认：
- OmniCtrl 源文件均已参与编译；
- `control_config.c` 已参与编译；
- Manifest 中引用的工程头文件可以正确找到；
- 没有未定义符号或重复定义；
- 固件可以正常启动。
完成后将固件烧录至 MCU。

> 第一次启动前，还需要为设备准备一张有效的控制拓扑，无有效图会导致系统初始化失败。  
> 接下来使用 OmniCtrl Studio 完成这一过程。

---

# 7. 配置 OmniCtrl Studio

OmniCtrl Studio 位于：
```text
OmniCtrl/studio/
```
Studio 与 MCU 端需要使用相同的工程配置。

将当前使用的：
```text
OmniCtrl/firmware/omni_manifest.json
```
同步到：
```text
OmniCtrl/studio/OmniCtrl/definitions/omni_manifest.json
```
确保两份文件内容一致。

安装 Studio 所需依赖：
```bash
pip install dearpygui
```

然后运行：
```bash
python OmniCtrl/studio/OmniCtrl/main.py
```

如果配置正确，Studio 会根据当前 Manifest 自动加载：
- 可用控制算子；
- 工程输入数据；
- 工程输出数据。

---

# 8. 创建第一张控制拓扑

第一次测试不建议直接搭建复杂 PID。

先建立一个最简单的：
```text
Input → Gain → Output
```
用于验证整个 OmniCtrl 工作流程。

在 Studio 中：
1. 找到前面配置的 `Input`；
2. 添加一个 Gain 算子；
3. 找到 `Output`；
4. 将 `Input` 连接至 Gain 输入；
5. 将 Gain 的增益设置为 `1`；
6. 将 Gain 输出连接至 `Output`。

最终效果类似：
```text
┌─────────┐
│  Input  │
└────┬────┘
     │
     ▼
┌─────────┐
│  Gain   │
│ Gain=1  │
└────┬────┘
     │
     ▼
┌─────────┐
│ Output  │
└─────────┘
```

# 9. 生成控制数据

完成控制拓扑后关闭 OmniCtrl Studio。

Studio 会检查当前拓扑并生成对应的控制数据，在终端中可以看到类似：
```text
Hex Result: 0x...
```
这段数据就是最终需要发送给 MCU 的控制拓扑。

OmniCtrl 本身不限制数据如何下发。可以根据项目选择：
```text
UART
RS485
USB
CAN
网络
其他自定义通信方式
```

> ⚠️ **当前版本需要正常关闭 Studio 后才会返回生成的控制拓扑数据。**

---

# 10. 将第一张拓扑下发至 MCU

目标工程需要提供一种方式：
```text
接收 Studio 生成的数据
        ↓
验证数据
        ↓
提取控制拓扑
        ↓
保存
        ↓
重新启动
        ↓
ControlCore_Init()
```

OmniCtrl 已提供：
```c
Control_Comm_Get_Graph();
```
用于从接收到的数据中校验并提取控制拓扑。

一个典型流程为：
```c
uint32_t graph_size;

graph_size = Control_Comm_Get_Graph(rx_buffer, rx_size);

if(graph_size != 0)
{
    /* 保存新的控制拓扑 */
    Save_Graph(rx_buffer, graph_size);
}
```
具体的接收、保存以及设备重新启动方式由目标工程决定，并在引导模式中完成对应实现。

---

# 11. 重启并验证

重新启动设备，启动过程中：
```text
读取已经保存的 Graph
        ↓
ControlCore_Init()
        ↓
建立控制关系
        ↓
周期执行 ControlCore_Update()
```

对于前面创建的：
```text
Input → Gain(1) → Output
```

如果整个流程正确，则最终应得到：
```text
Output = Input * 1
```

至此已经完成从：
**MCU 工程接入 → 配置 → Studio 建图 → 数据下发 → MCU 执行**
的完整 OmniCtrl 工作流程。

---

# 12. 总结

```
1. 配置 omni_manifest.json
2. 使用 config_c.py 生成代码
3. 编写 Boot_Process()，并在合适位置对 control_into_bootloader 置位
4. 注册 Boot_Process，读取 graph，初始化控制系统
5. 使用 OmniCtrl Studio 生成拓扑图编码
6. 触发 Boot_Process 传输编码，并完成校验与解码
7. 运行系统
```
