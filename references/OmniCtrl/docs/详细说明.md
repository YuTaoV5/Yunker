# OmniCtrl 详细说明

本文档用于进一步说明 OmniCtrl 的设计方式、MCU 端与 Studio 的协作关系、控制拓扑的数据组织方式以及二次开发方法。

如果只是希望快速将 OmniCtrl 加入工程并完成第一次控制拓扑下发，请优先阅读 [快速开始](./快速开始.md)。

---

# 1. 整体设计

## 1.1 设计思路

OmniCtrl 希望解决的核心问题，是将**控制功能本身**与**控制功能之间的组合关系**进行分离。

传统 MCU 控制程序通常直接在代码中组织调用关系：
```text
采集数据 -> PID -> 限幅 -> 输出
```

如果希望将其改为：
```text
采集数据 -> 滤波 -> PID -> 斜坡处理 -> 限幅 -> 输出
```
通常需要重新调整程序结构、编译并烧录。

OmniCtrl 将 PID、滤波、限幅等控制功能封装为具有统一接口的**算子**，控制关系则由 Studio 单独设计，因此整个系统可以划分为：
```text
                    omni_manifest.json
                       ↙          ↘
                      ↙            ↘
              MCU 端配置            Studio
                  │                   │
                  │              控制拓扑设计
                  │                   │
                  │                   ↓
                  │               Graph 数据
                  │                   │
                  └───────── MCU ◀────┘
```
MCU 端负责提供和执行控制功能，Studio 负责决定这些控制功能如何连接。

---

## 1.2 OmniCtrl 的几个核心概念

### 算子

算子是 OmniCtrl 中最基本的控制单元，例如：
- Gain：增益；
- Limit：限幅；
- Offset：偏移；
- Positional PID：位置式 PID；
- Mean Filter：均值滤波。

每个算子具有若干输入或配置参数，并产生一个统一的 `signal_t` 输出，例如 Gain：
```text
Input ──┐
        ├── Gain ──→ Output
Gain ───┘
```

其中 `Input` 和 `Gain` 都属于算子的参数。参数既可以直接填写固定值，也可以连接到其他数据。

---

### 外部参数

外部参数用于将 MCU 工程中已经存在的数据提供给 OmniCtrl，例如：
```c
Motor_A.encoder_->Count_
Motor_A.target_speed_
```

经过配置后，可以在 Studio 中表现为对应的输入节点：
```text
Speed_A ──────→ PID
```

OmniCtrl 并不会复制这些变量。初始化完成后，算子内部保存的是对应变量的指针，因此应用程序只需要正常更新原变量，控制计算便能够直接读取最新数据。

---

### 输出参数

输出参数用于在 Studio 中提供控制拓扑的最终输出位置，例如：
```text
Speed
  ↓
 PID
  ↓
Output_A
```

当前实现中，输出结果最终通过：
```c
ctrl_output_signal[]
```
提供给应用层。

应用程序可以根据实际需求处理这些结果：
```c
ControlCore_Update();

Motor_SetSpeed(&Motor_A, ctrl_output_signal[0]);
Motor_SetSpeed(&Motor_B, ctrl_output_signal[1]);
```
因此 OmniCtrl 不会限制最终结果必须用于 PWM、电机、DAC 或其他具体外设。

---

### Manifest

`omni_manifest.json` 用于描述当前工程提供给 OmniCtrl 的控制能力，主要包括：
```text
有哪些算子
算子有哪些参数
有哪些 MCU 外部数据
有哪些控制输出
```

同一份配置分别用于：
```text
                    omni_manifest.json
                       ↙          ↘
                      ↙            ↘
               config_c.py        Studio
                    ↓               ↓
             MCU 配置代码       图形化节点
```
因此 Manifest 是 MCU 端与 Studio 保持一致的重要桥梁。

---

### Graph

Graph 是 Studio 根据用户设计的控制拓扑生成的数据，它描述的不是具体 C 代码，而是：
```text
创建哪些算子
      +
参数如何设置
      +
算子之间如何连接
      +
哪些算子的结果需要输出
```
MCU 获得 Graph 后，可以根据其中的信息建立对应的控制关系。

---

# 2. Manifest 与配置生成

## 2.1 Manifest 结构

当前 Manifest 的主要结构如下：
```json
{
    "version": "1.0",
    "signal_type": "CTRL_PARAM_FLOAT",

    "modules_include": [],

    "CtrlModules": [],

    "params_include": [],

    "Params": [],

    "OutputParams": []
}
```
不同字段分别服务于 MCU 配置生成和 Studio。

|字段|作用|
|---|---|
|`version`|配置文件版本|
|`signal_type`|OmniCtrl 信号实际使用的数据类型|
|`modules_include`|自动生成 MCU 配置代码时需要包含的算子头文件|
|`CtrlModules`|当前工程支持的算子|
|`params_include`|外部变量所在的头文件|
|`Params`|提供给 OmniCtrl 使用的 MCU 外部变量|
|`OutputParams`|Studio 中允许连接的控制输出|

---

## 2.2 signal_type

MCU 端统一使用：
```c
typedef float signal_t;
```
表示主要控制信号。

因此当前配置为：
```json
"signal_type": "CTRL_PARAM_FLOAT"
```
Studio 根据该字段决定 `signal_t` 在控制数据中的实际存储格式。

> ⚠️ `signal_type` 必须与 MCU 端实际的 `signal_t` 保持一致。

当前项目按照 `float` 设计和验证。如果修改 `signal_t`，需要同时检查数据编码、参数转换及相关算子实现。

---

# 2.3 算子配置

一个算子在 Manifest 中类似：
```json
{
    "Name": "MODULE_GAIN",
    "Type": "GainController_t",
    "Init": "GainController_Init",

    "Params": [
        {
            "Name": "GAIN_PORT_INPUT",
            "Type": "CTRL_PARAM_SIGNAL_T"
        },
        {
            "Name": "GAIN_PORT_GAIN",
            "Type": "CTRL_PARAM_SIGNAL_T"
        }
    ]
}
```
其中：

|字段|作用|
|---|---|
|`Name`|MCU 端算子类型，同时作为 Studio 中的算子名称|
|`Type`|算子结构体类型，用于计算实例所需内存大小|
|`Init`|算子初始化函数|
|`Params`|算子提供的全部参数端口|

配置生成脚本最终会生成类似：
```c
CtrlModule_Registry_Init(
    MODULE_GAIN,
    sizeof(GainController_t),
    GainController_Init
);
```
因此 MCU 可以根据 Graph 中的算子类型动态创建对应结构体并执行初始化。

---

## 2.4 算子顺序约束

这是二次开发时非常重要的一项约束。

MCU 中的算子类型定义为：
```c
typedef enum
{
    MODULE_GAIN = 0,
    MODULE_LIMIT,
    MODULE_OFFSET,
    ...
    MODULE_NUM,
} ModuleType_t;
```

而 Studio 在加载 Manifest 时，会按照 `CtrlModules` 的排列顺序分配算子类型 ID：
```text
第 0 个 → Type ID 0
第 1 个 → Type ID 1
第 2 个 → Type ID 2
...
```
最终 Graph 保存的是这个数字 ID。

因此：

> ⚠️ **Manifest 中 `CtrlModules` 的顺序必须与 MCU 端 `ModuleType_t` 枚举顺序保持一致。**

例如 MCU 为：
```text
0 MODULE_GAIN
1 MODULE_LIMIT
2 MODULE_OFFSET
```

那么 Manifest 也必须按照：
```text
MODULE_GAIN
MODULE_LIMIT
MODULE_OFFSET
```

如果只修改顺序而不修改 MCU 枚举，Studio 与 MCU 将对同一个数字产生不同理解。

---

## 2.5 参数顺序约束

同样，每个算子参数在 MCU 中通过枚举确定参数 ID，例如：
```c
typedef enum
{
    GAIN_PORT_INPUT = 0,
    GAIN_PORT_GAIN,
} GainController_Ports;
```

Studio 则按照 Manifest 中 `Params` 的排列顺序分配参数 ID，因此：
```json
"Params": [
    {
        "Name": "GAIN_PORT_INPUT"
    },
    {
        "Name": "GAIN_PORT_GAIN"
    }
]
```
的顺序也不能随意调整。

> ⚠️ **Manifest 中算子参数顺序必须与对应算子的 Port 枚举顺序一致。**

这是新增算子时最需要注意的两个顺序约束：
```text
ModuleType_t
     ↕
CtrlModules 顺序

Port Enum
     ↕
Params 顺序
```

---

# 2.6 外部参数

外部参数配置例如：
```json
{
    "Name": "Speed_A",
    "Type": "CTRL_PARAM_SIGNAL_T",
    "Ptr": "Motor_A.encoder_->Count_"
}
```

配置生成脚本会转换为：
```c
CtrlModule_Registry_Param(
    "Speed_A",
    CTRL_PARAM_SIGNAL_T,
    &(Motor_A.encoder_->Count_),
    0
);
```
三个字段分别表示：

### Name
Studio 中显示的名字，同时参与 MCU 端参数识别。例如：
```text
Speed_A
```
会在 Studio 中成为一个外部输入节点。

### Type
实际变量的数据类型。

### Ptr
对应的 MCU 变量或表达式。该字段会直接展开到自动生成的 C 代码中，因此：
```json
"Ptr": "Motor_A.encoder_->Count_"
```
最终直接得到：
```c
&(Motor_A.encoder_->Count_)
```

---

## 2.7 外部参数的名称匹配

MCU 不会在 Graph 中保存完整的变量名称。注册参数时，MCU 使用 FNV-1a 32-bit Hash 将名称转换为数字：
```text
"Speed_A"
    ↓
FNV-1a
    ↓
32-bit Hash
```
Studio 在生成最终控制数据时，也会根据外部参数名称生成相同的 FNV-1a Hash。

初始化时：
```text
Graph 中的 Hash
        ↓
参数注册表查找
        ↓
得到 MCU 变量指针
        ↓
连接至算子
```
因此外部参数最终通过**名称**建立关联。

修改外部参数名称后，需要同时重新：
1. 生成 MCU 配置代码；
2. 更新 Studio 使用的 Manifest；
3. 重新生成控制拓扑。

---

# 2.8 参数类型约束

外部参数最终通过真实指针连接至算子。因此对于动态连接：

> ⚠️ **Manifest 中声明的数据类型必须与实际变量类型、目标算子参数类型正确对应。**

例如当前：
```c
typedef float signal_t;
```
则：
```json
"Type": "CTRL_PARAM_SIGNAL_T"
```
对应变量应当实际为 `signal_t`，也就是当前版本中的 `float`。

不要直接将：
```c
int value;
```
配置为：
```json
"Type": "CTRL_PARAM_SIGNAL_T"
```

否则算子会按照 `float *` 使用该地址，可能得到错误结果甚至造成系统异常。

对于指针形式的动态参数，MCU 端不会进行数值类型转换。只有 Graph 中直接保存的静态数值参数，才可以通过 `CtrlModule_Param_Transform()` 在不同数值类型之间进行转换。

---

# 2.9 输出参数

输出参数例如：
```json
{
    "Name": "Target_Speed_A",
    "Ptr": "Motor_A.target_speed_"
}
```
Studio 会为其生成一个输出节点。

当前控制核心最终通过：
```c
ctrl_output_signal[]
```
将结果交给应用程序，因此应用层仍然负责决定如何使用最终输出。

例如：
```c
ControlCore_Update();

Motor_SetSpeed(&Motor_A, ctrl_output_signal[0]);
```
当前生成脚本仍会根据 `Ptr` 生成输出参数注册代码，因此配置中的表达式应保持有效。

需要特别注意：

> `ctrl_output_signal[]` 的排列顺序与最终 Graph 中已经连接的输出节点顺序一致。

如果应用程序依赖固定的：
```c
ctrl_output_signal[0]
ctrl_output_signal[1]
```
则应该确保对应的输出节点均按照预期连接。

---

# 2.10 配置代码生成

`config_c.py` 主要完成三件事：

### 生成依赖头文件
根据：
```json
"modules_include"
```
生成算子头文件引用；

根据：
```json
"params_include"
```
生成应用变量对应的头文件引用。

---

### 注册算
根据：
```json
"CtrlModules"
```
生成：
```c
Ctrl_Config_ModuleInit()
```

其中依次调用：
```c
CtrlModule_Registry_Init();
```
完成算子结构体大小和初始化函数注册。

---

### 注册参数
根据：
```json
"Params"、"OutputParams"
```
生成：
```c
Ctrl_Config_ParamInit()
```

最终生成的：
```text
control_config.c
```
属于自动生成文件。正常情况下不需要手动修改。

---

# 3. OmniCtrl MCU 端

## 3.1 基本结构

MCU 端主要由三部分组成：
```text
firmware/
│
├── bases/
│   ├── control_types
│   ├── control_config
│   ├── control_comm
│   ├── control_log
│   └── algorithms_math
│
├── methods/
│   ├── ctrl_factory
│   ├── ctrl_registry
│   ├── ctrl_wiring
│   ├── ctrl_pool
│   └── ctrl_hash
│
├── modules/
│   └── 各控制算子
│
├── control_core.c
└── control_core.h
```

其中：
- `bases` 提供基础类型、通信、日志及自动生成配置；
- `methods` 负责算子创建、注册、连接和内存管理；
- `modules` 保存具体控制算子；
- `control_core` 负责根据 Graph 建立控制关系并周期执行所有算子。

---

# 3.2 统一算子接口

所有算子的第一个成员都是：
```c
ControlModule_t base_;
```

`ControlModule_t` 定义为：
```c
typedef struct
{
    signal_t output_;

    ModuleType_t type_;

    void (*Process)(void *self);

    char (*Connect)(void *self, char param_id, CtrlModule_Param_t param);

    char (*SetStaticParam)(void *self, char param_id, CtrlModule_Param_t param);
} ControlModule_t;
```
因此所有算子都具有相同的三个核心接口：

### Process
执行一次算子计算。

### Connect
将某个参数连接到外部变量或其他算子的输出。

### SetStaticParam
直接设置固定参数。

这种统一接口使控制核心不需要了解 PID、Gain 或 Filter 的具体结构。
对于控制核心而言，所有算子都可以统一处理为：
```c
ControlModule_t *
```

---

# 3.3 静态参数与动态参数

OmniCtrl 中的算子参数有两种使用方式。

## 静态参数

例如：
```text
Gain = 2.0
```
该值直接保存在 Graph 中。

初始化时：
```text
Graph 中的数值
      ↓
SetStaticParam()
      ↓
算子内部 xxx_static_
```

例如 Gain 中：
```c
signal_t gain_static_;
signal_t *gain_;
```
默认：
```c
gain_ = &gain_static_;
```
因此静态参数依然通过统一的指针方式参与后续计算。

---

## 动态参数

参数也可以连接至：

1. MCU 外部变量；
2. 其他算子的输出。

例如：
```text
Speed_A ─────────→ PID.Input
```
或者：
```text
PID.Output ──────→ Limit.Input
```

初始化完成后，算子内部直接保存对应数据的指针。因此每次计算时：
```c
*pid->input_
```
读取到的就是当前最新数据，不需要额外执行参数同步。

---

# 3.4 三种参数来源

Graph 中的一个参数最终可以有三种来源：
```text
                算子参数
             ↙      ↓      ↘
            ↙       ↓       ↘
        静态值   外部参数   前级算子
```

MCU 通过参数描述字节的低两位进行区分。

|类型|含义|
|---|---|
|`00`|静态参数|
|`01`|MCU 外部参数|
|`10`|其他算子的输出|

---

## 静态参数

调用：
```c
CtrlModule_Wiring_Param()
```
最终进入算子的：
```c
SetStaticParam()
```

---

## 外部参数

Graph 保存外部参数名称对应的 Hash。MCU 通过：
```c
CtrlModule_Get_Param()
```
从注册表中查找真实变量指针，再调用：
```c
CtrlModule_Wiring_hash()
```
完成连接。

---

## 前级算子输出

Graph 中保存前级算子的索引。MCU 直接取得：
```c
&Ctrl_Factory_Get_Module(index)->output_
```
并调用：
```c
CtrlModule_Wiring_ptr()
```
连接至目标参数。

因此：
```text
Module A.Output
       ↓
Module B.Input
```

在 MCU 内部最终表现为：
```text
Module B.input_
       ↓
指向
       ↓
Module A.base_.output_
```
数据不需要在不同算子之间反复复制。

---

# 3.5 算子注册

`CtrlModule_Registry_Init()` 用于登记：
```text
算子类型
+
结构体大小
+
初始化函数
```

注册信息类似：
```text
MODULE_GAIN
    ↓
sizeof(GainController_t)
    ↓
GainController_Init
```

当 Graph 要求创建一个 `MODULE_GAIN` 时，控制核心便可以根据注册信息：
1. 知道需要多少内存；
2. 分配对应空间；
3. 调用正确的初始化函数。

---

# 3.6 算子工厂

算子实例由：
```c
Ctrl_Factory_CreateModule()
```
统一创建。

流程为：
```text
Graph 中的 ModuleType
        ↓
查询注册表
        ↓
得到结构体大小和 Init
        ↓
申请内存
        ↓
调用 Init
        ↓
保存模块指针
```

当前：
```c
#define MAX_CONTROL_MODULES 30
```
因此一张控制拓扑最多创建 30 个算子实例。

---

# 3.7 内存池

算子实例并没有直接使用 `malloc()`，OmniCtrl 预先分配：
```c
#define MODULE_MEM_POOL_SIZE (1024 * 8)
```
即 8 KB 内存池。

创建算子时：
```text
CtrlPool_Malloc()
```
只需要向后移动内存池位置。

当重新初始化控制系统时：
```c
Ctrl_Factory_Reset()
```
会调用：
```c
CtrlPool_FreeAll()
```
一次性释放全部算子。

这种方式不支持单独释放某一个算子，但与 OmniCtrl 当前“整张控制拓扑统一建立”的使用方式一致。

---

# 3.8 ControlCore_Init()

`ControlCore_Init()` 是 MCU 端最核心的初始化入口。整体过程可以概括为：
```text
ControlCore_Init()
      │
      ├── 注册当前工程支持的算子
      │
      ├── 注册当前工程的外部参数
      │
      ├── 清空已有算子
      │
      ├── 检查是否进入拓扑下载模式
      │
      ├── 读取 Graph
      │
      ├── 创建算子
      │
      ├── 设置静态参数
      │
      ├── 连接外部参数
      │
      ├── 连接算子输出
      │
      └── 记录最终输出
```

---

## 3.9 Graph 解析

Graph 从第一个字节开始依次读取。当读取到：
```text
< 0x80
```
时，将其作为算子类型 ID：
```c
Ctrl_Factory_CreateModule(graph[graph_index]);
```
随后继续读取该算子的参数。

当遇到：
```text
0xFF
```
表示当前算子参数结束。

当算子段全部结束后，Graph 中还可以包含输出节点信息。
最终再次出现结束标志后，初始化完成。

---

# 3.10 ControlCore_Update()

初始化结束后，控制结构已经建立完成。因此每个控制周期并不需要重新分析拓扑。

`ControlCore_Update()` 只需要：
```text
第 0 个算子 Process()
        ↓
第 1 个算子 Process()
        ↓
第 2 个算子 Process()
        ↓
...
        ↓
整理最终输出
```

对应代码逻辑为：
```c
for(...)
{
    module = Ctrl_Factory_Get_Module(i);
    module->Process(module);
}
```
这里之所以可以直接按顺序执行，是因为 Studio 已经提前完成了拓扑排序。
因此较复杂的图关系分析由 PC 完成，MCU 主要负责按照已经确定的顺序进行控制计算。

---

# 4. OmniCtrl Studio

## 4.1 Studio 的职责

Studio 主要负责：
```text
读取 Manifest
      ↓
创建可用算子和参数
      ↓
用户搭建控制拓扑
      ↓
检查连接关系
      ↓
拓扑排序
      ↓
生成 Graph
```
Studio 不负责具体 UART、USB 或 CAN 通信。
生成 Graph 后，如何把数据传输到设备由具体工程决定。

---

# 4.2 ManifestLoader

Studio 首先通过：
```python
ManifestLoader
```
解析 `omni_manifest.json`。

加载后建立：
```text
Manifest
├── modules
├── ext_params
├── out_params
├── signal_type
└── hash
```

其中每一个算子会进一步生成：
```text
Module
├── father_name
├── type_id
├── type_name
├── type_init
└── params[]
```

每个参数则保存：
```text
Name
Type
ID
Value
Static / Dynamic
```
因此 Studio 的节点不是写死在 Python 代码中的，而是根据 Manifest 动态生成。

---

# 4.3 节点类型

Studio 中主要存在三类节点。

## 外部参数节点

来源于：
```json
"Params"
```
只有输出端口：
```text
┌─────────────┐
│   Speed_A   │───→
└─────────────┘
```
用于向控制拓扑提供 MCU 数据。

---

## 算子节点

来源于：
```json
"CtrlModules"
```
例如：
```text
      ┌──────────────┐
─────→│ Input        │
      │     PID      │─────→
─────→│ Setpoint     │
      │ Kp / Ki / Kd │
      └──────────────┘
```
参数既可以填写固定值，也可以连接其他节点。

---

## 输出节点

来源于：
```json
"OutputParams"
```
只提供输入端：
```text
              ┌─────────────┐
─────────────→│  Output_A   │
              └─────────────┘
```
当前 Studio 要求输出节点连接到算子的输出，外部参数不能直接连接至输出节点。

---

# 4.4 参数连接

对于一个算子参数：
```text
PID.Kp
```
用户可以：

### 直接填写
```text
Kp = 2.0
```
表示静态参数。

### 连接外部参数
```text
External_Kp ──→ PID.Kp
```
表示该值由 MCU 变量动态提供。

### 连接其他算子
```text
Gain.Output ──→ PID.Setpoint
```
表示该参数来自前级算子的计算结果。

一个输入端口只能存在一条有效连接。一个算子的输出则可以连接至多个目标参数。

---

# 4.5 参数类型检查

Studio 根据 Manifest 中声明的 `Type` 检查连线类型。相同类型可以直接连接。

同时：
```text
CTRL_PARAM_SIGNAL_T
```
与 `signal_type` 对应的实际信号类型被视为兼容。

不过 MCU 最终使用真实指针完成动态连接，因此：

> 对于动态参数，建议始终让两端使用完全匹配的类型定义，不要依赖隐式类型转换。

---

# 4.6 拓扑排序

Studio 在生成最终数据前，会对所有算子进行拓扑排序。
例如用户设计：
```text
Input
  ↓
Gain
  ↓
PID
  ↓
Limit
```
则最终执行顺序为：
```text
Gain → PID → Limit
```
外部参数不参与排序，因为它们在每个控制周期开始前已经存在。
输出节点也不参与排序。

---

# 4.7 环路检测

如果存在算子之间的直接闭环：
```text
A → B
↑   ↓
└───┘
```
Studio 无法得到有效的拓扑顺序，因此会拒绝生成控制数据。

这并不意味着 OmniCtrl 无法实现闭环控制。
例如电机速度闭环实际可以表示为：
```text
编码器速度
     ↓
    PID
     ↓
  电机输出
     ↓
   实际电机
     ↓
下一周期重新读取编码器
```
反馈通过 MCU 外部变量和实际控制对象跨控制周期形成，而不是在同一次算子计算中建立直接的数据环。

---

# 4.8 `.omni` 工程文件

Studio 可以将当前编辑内容保存为 `.omni` 文件。`.omni` 保存的是**编辑工程**，而不是最终下发给 MCU 的 Graph。

主要内容包括：
```text
Metadata
    └── ManifestHash

Nodes
    ├── 算子类型
    ├── 算子名称
    ├── 参数
    └── UI 位置

Links
    └── 节点连接关系
```

因此：
```text
.omni
= 可继续编辑的 Studio 工程

Graph
= 最终发送给 MCU 的控制数据
```
两者用途不同。

---

# 4.9 ManifestHash

Studio 保存 `.omni` 时，会同时保存当前 Manifest 的 Hash。

重新打开工程时：
```text
.omni ManifestHash
        ↓
与当前 Manifest 比较
        ↓
一致 → 允许恢复
不一致 → 拒绝导入
```
这样可以避免使用旧工程去加载已经发生较大变化的算子定义或参数结构。

---

# 5. Graph 与通信

## 5.1 Graph 的目的

Graph 的目标不是保存所有 UI 信息，而是只保存 MCU 建立控制关系所需的信息。

因此其中不包括：
- 节点坐标；
- 节点显示名称；
- UI 布局；
- 工程文件信息。

只包含：
```text
算子类型
参数设置
参数连接
最终输出
```

---

# 5.2 Graph 生成过程

Studio 首先执行：
```text
用户拓扑
   ↓
合法性检查
   ↓
拓扑排序
   ↓
重新确定 MCU 算子顺序
   ↓
参数编码
   ↓
输出编码
   ↓
添加校验
```

值得注意的是：

> Graph 中模块之间的连接使用的是**排序后的算子索引**，不是 Studio 内部原始节点 ID。

因此 MCU 不需要重新进行拓扑排序。

---

# 5.3 Graph 基本结构

当前控制数据大致由以下部分组成：
```text
┌─────────────────────────┐
│ Magic: 20 13 14         │
├─────────────────────────┤
│ Frame Length            │
├─────────────────────────┤
│                         │
│      Graph Body         │
│                         │
├─────────────────────────┤
│ CRC32                   │
└─────────────────────────┘
```

帧头固定为：
```text
20 13 14
```
用于区分 OmniCtrl 控制数据。

---

# 5.4 算子编码

每个算子首先保存：
```text
Module Type ID
```

随后依次保存需要设置或连接的参数。参数包含：
```text
Param ID
Param Description
Param Data
```

参数描述字节包含：
```text
高 4 位：数据类型
中 2 位：静态参数数据长度
低 2 位：参数来源
```
参数来源为：
```text
00 → 静态值
01 → 外部参数
10 → 前级算子输出
```

---

# 5.5 静态参数

静态参数直接保存实际数值。支持的长度编码包括：
```text
1 Byte
2 Byte
4 Byte
8 Byte
```

MCU 读取后构造 `CtrlModule_Param_t`，再通过：
```c
SetStaticParam()
```
写入具体算子。

---

# 5.6 外部参数

外部参数保存：
```text
FNV-1a 32-bit Hash
```
MCU 根据 Hash 从参数注册表中找到对应变量指针。

因此 Graph 本身不需要知道：
```text
Motor_A.encoder_->Count_
```
这样的具体 C 表达式。

它只需要知道：
```text
Speed_A
```
对应的 Hash。

---

# 5.7 算子之间的连接

如果参数来自另一个算子：
```text
Gain → PID
```

Graph 保存的是：
```text
Gain 在最终执行顺序中的索引
```

MCU 初始化时取得：
```c
&source_module->output_
```
并将该地址交给目标算子。

---

# 5.8 输出编码

Studio 会遍历已经连接的输出节点，并记录：
```text
0x80 | SourceModuleIndex
```
MCU 初始化后将这些模块索引保存起来。

每次：
```c
ControlCore_Update()
```
结束后，再将对应算子的输出写入：
```c
ctrl_output_signal[]
```
应用层即可取得最终结果。

---

# 5.9 CRC32 校验

Studio 在控制数据末尾附加 CRC32。当前实现采用：
```text
Polynomial : 0xEDB88320
Initial    : 0xFFFFFFFF
```

MCU 通过：
```c
Control_Comm_Get_Graph()
```
完成：
1. 帧头检查；
2. 长度检查；
3. CRC32 校验；
4. 移除通信帧头和校验数据；
5. 得到真正的 Graph 内容。

因此应用层不需要自行解析 Graph 内部结构。

---

# 5.10 拓扑下载模式

OmniCtrl 本身不规定 Graph 必须通过什么接口传输。

目标工程需要提供一个拓扑下载处理函数，例如：
```c
Boot_Process()
```

并注册：
```c
Control_Comm_Register_Bootloader(Boot_Process);
```

当下载标志有效时：
```text
ControlCore_Init()
       ↓
检测下载模式
       ↓
Boot_Process()
       ↓
接收控制数据
       ↓
Control_Comm_Get_Graph()
       ↓
保存 Graph
       ↓
重新启动
```

具体通信和存储方式由工程决定。

DC Motor Driver 当前采用：
```text
UART
  +
内部 Flash
```

其他工程也可以采用：
```text
USB + Flash
CAN + EEPROM
RS485 + Flash
网络 + 文件系统
```
这些方式不会影响 OmniCtrl 核心代码。

---

# 6. 控制算子与扩展

## 6.1 当前提供的算子

当前 MCU 端提供以下算子：

|算子|主要作用|主要参数|
|---|---|---|
|Gain|输入乘以增益|Input、Gain|
|Limit|输出限幅|Input、Min、Max|
|Offset|输入增加偏置|Input、Offset|
|Positional PID|位置式 PID|Input、Kp、Ki、Kd、Setpoint 等|
|Incremental PID|增量式 PID|Input、Kp、Ki、Kd、Setpoint 等|
|Ramp Injector|按固定步长跟随输入|Input、Rise Step、Fall Step|
|Curve Accel|根据误差大小进行曲线加减速|Input、Accel Gain、Decel Gain、Max Step|
|Branch Judge|带迟滞的条件分支|Condition、True Input、False Input、Threshold、Hysteresis|
|Mean Filter|滑动均值滤波|Input、Window Size|

---

# 6.2 默认参数

算子创建后会先使用内部默认参数。

例如：

|算子|默认值|
|---|---|
|Gain|Gain = 1|
|Offset|Offset = 0|
|Limit|Min = 0，Max = 0|
|PID|Kp/Ki/Kd/Setpoint 等均为 0|
|Ramp Injector|Rise/Fall Step = 0|
|Curve Accel|Gain/Max Step = 0|
|Branch Judge|Threshold/Hysteresis = 0|
|Mean Filter|Window Size = 1|

Studio 只会将需要设置或连接的参数写入 Graph。

因此：

> 对于依赖特定参数值的控制拓扑，建议在 Studio 中明确设置关键参数，而不要依赖算子的内部默认值。

---

# 6.3 算子的基本结构

以 Gain 为例：
```c
typedef struct
{
    ControlModule_t base_;

    signal_t gain_static_;

    signal_t *input_;
    signal_t *gain_;

    char is_wired_;
} GainController_t;
```

一个典型算子通常包含：
```text
ControlModule_t
      +
静态参数存储
      +
动态参数指针
      +
算法内部状态
```

---

# 6.4 Connect()

`Connect()` 用于动态连接。例如：
```c
case GAIN_PORT_INPUT:
    gain_ctrl->input_ = ...;
    break;
```

动态来源可能是：
```text
MCU 外部变量
或
前级算子 output_
```
由于最终保存的是真实指针，因此类型必须正确对应。

---

# 6.5 SetStaticParam()

`SetStaticParam()` 用于处理 Studio 中直接填写的固定数值。例如：
```c
case GAIN_PORT_GAIN:
    gain_static_ = ...;
    break;
```
并不是所有参数都必须允许静态设置。

例如通常：
```text
Input
```
应该通过连接获得。而：
```text
Gain
Kp
Ki
Threshold
```
才适合作为固定配置。
具体由每个算子的 `SetStaticParam()` 实现决定。

---

# 6.6 Process()

`Process()` 执行实际控制算法。例如 Gain：
```c
output = input × gain
```
最终必须将结果写入：
```c
base_.output_
```
这样后续算子才能通过指针取得该结果。

---

# 6.7 Init()

算子的公开初始化函数负责：
1. 设置静态默认参数；
2. 初始化内部状态；
3. 将参数指针指向默认静态值；
4. 设置 `Process`；
5. 设置 `Connect`；
6. 设置 `SetStaticParam`；
7. 设置模块类型。

例如：
```c
base_.Process = Xxx_Process;
base_.Connect = Xxx_Connect;
base_.SetStaticParam = Xxx_SetStaticParam;
base_.type_ = MODULE_XXX;
```

---

# 6.8 新增算子

如果现有算子无法满足需求，可以按照以下流程增加新算子。

### 第一步：增加模块类型

在：
```c
ModuleType_t
```
中加入：
```c
MODULE_MY_CONTROLLER
```
建议在 `MODULE_NUM` 前追加。

---

### 第二步：定义参数 ID

例如：
```c
typedef enum
{
    MY_PORT_INPUT = 0,
    MY_PORT_GAIN,
} MyController_Ports;
```

---

### 第三步：定义结构体

结构体第一个成员必须为：
```c
ControlModule_t base_;
```
随后定义：
```text
静态参数
动态参数指针
算法状态
```

---

### 第四步：实现三个接口

实现：
```c
Process()
Connect()
SetStaticParam()
```
其中仅：
```c
MyController_Init()
```
作为对外初始化函数。

---

### 第五步：初始化基类

在 `Init()` 中设置：
```c
base_.Process
base_.Connect
base_.SetStaticParam
base_.type_
```
并设置所有默认参数。

---

### 第六步：加入 Manifest

在：
```json
"modules_include"
```
加入新头文件。

然后在：
```json
"CtrlModules"
```
中按照 `ModuleType_t` 对应的位置增加：
```json
{
    "Name": "MODULE_MY_CONTROLLER",
    "Type": "MyController_t",
    "Init": "MyController_Init",

    "Params": [
        {
            "Name": "MY_PORT_INPUT",
            "Type": "CTRL_PARAM_SIGNAL_T"
        },
        {
            "Name": "MY_PORT_GAIN",
            "Type": "CTRL_PARAM_SIGNAL_T"
        }
    ]
}
```
参数顺序必须与：
```c
MyController_Ports
```
保持一致。

---

### 第七步：重新生成配置

重新运行：
```text
config_c.py
```
并同步 Studio 使用的 Manifest。再次启动 Studio 后，新算子便会自动出现在工具栏中。
因此新增普通控制算子通常不需要修改 Studio Python 源码。

---

# 7. MCU 工程适配

## 7.1 平台无关方式

OmniCtrl MCU 端没有直接调用：
```text
STM32 HAL
NXP SDK
CH32 SDK
```
等特定平台 API。它所依赖的主要外部能力由目标工程提供。

例如：
```text
Graph 存储
Graph 接收
日志发送
控制周期调度
```
因此 MCU 平台差异主要保留在具体应用工程中。

---

# 7.2 初始化接入

一个典型接入过程为：
```text
注册拓扑下载处理函数
        ↓
可选：注册日志发送函数
        ↓
读取已经保存的 Graph
        ↓
ControlCore_Init()
```

DC Motor Driver 中的实际结构为：
```c
Control_Comm_Register_Bootloader(Boot_Process);

Control_Log_Tx_Register(Ctrl_Tx);

Flash_Read(..., graph, ...);

ControlCore_Init();
```

---

# 7.3 控制周期

一个典型控制周期可以理解为：
```text
更新输入数据
      ↓
ControlCore_Update()
      ↓
使用最终输出
```

例如：
```c
Encoder_Update(...);

ControlCore_Update();

Motor_SetSpeed(...);
```

因此 OmniCtrl 不要求使用特定调度方式。可以根据项目将更新函数放在：

- 定时器控制周期；
- RTOS 周期任务；
- 已有控制任务；
等适当位置。

对于 PID 等与采样周期相关的算子，应保证调用周期符合实际控制设计。

---

# 7.4 Graph 存储

OmniCtrl 只要求在：
```c
ControlCore_Init()
```
前，使：
```c
graph[]
```
中存在有效控制拓扑。至于 Graph 保存在哪里，由用户自行决定。

例如：
```text
内部 Flash
外部 Flash
EEPROM
文件系统
其他非易失存储
```
DC Motor Driver 使用 MCU Flash 保存 Graph。

---

# 7.5 日志接口

OmniCtrl 提供：
```c
Control_Log_Tx_Register()
```
注册日志发送函数。

之后内部日志统一通过：
```c
Control_Log()
```
输出。

如果没有注册发送函数，日志会直接忽略，因此日志功能不是 OmniCtrl 正常控制所必须的依赖。

---

# 8. DC Motor Driver 中的实际对应关系

DC Motor Driver 是当前 OmniCtrl 的完整应用示例。
其中各部分对应关系如下：

|OmniCtrl 概念|DC Motor Driver|
|---|---|
|MCU 外部输入|编码器速度、目标速度|
|控制算子|PID、Gain、Limit 等|
|输出节点|两路电机控制结果|
|MCU 接入|`APP_Ctrl_Init()`|
|周期执行|`APP_Ctrl_Process()`|
|Graph 存储|MCU Flash|
|Graph 下载|`Boot_Process()`|
|通信|UART|
|拓扑设计|OmniCtrl Studio|
|设备管理|Motor Controller Host|

---

## 8.1 初始化

实际代码：
```text
Motor_Init()
      ↓
注册 Boot_Process
      ↓
注册日志接口
      ↓
从 Flash 读取 Graph
      ↓
ControlCore_Init()
```

---

## 8.2 控制周期

实际结构：
```text
更新 Motor A 编码器
更新 Motor B 编码器
        ↓
ControlCore_Update()
        ↓
读取 ctrl_output_signal[]
        ↓
控制 Motor A / Motor B
```
这也是 OmniCtrl 在实际工程中的典型位置。

# 9. 当前实现的重要约束

本节集中记录当前代码中的重要使用条件。在进行配置或二次开发前建议阅读。

---

## 9.1 signal_t 当前为 float

当前：
```c
typedef float signal_t;
```
因此默认控制信号按照 32 位浮点数处理。

Manifest 中：
```json
"signal_type": "CTRL_PARAM_FLOAT"
```
应与其保持一致。

---

## 9.2 动态指针参数必须保证真实类型正确

静态数值可以进行数值类型转换。但外部参数和模块连接最终使用真实指针，因此不能依赖自动类型转换。错误的指针类型可能导致断言、错误数据甚至系统异常。

---

## 9.3 Manifest 顺序具有实际意义

必须保证：
```text
CtrlModules 顺序
=
ModuleType_t 枚举顺序
```
并保证：
```text
每个 Module.Params 顺序
=
该模块 Port 枚举顺序
```
当前代码不会自动根据 C 枚举名称重新排序。

---

## 9.4 控制拓扑不能包含直接模块环路

Studio 会在生成 Graph 前进行拓扑排序。存在直接算子闭环时将拒绝生成。闭环控制应通过 MCU 外部反馈量跨控制周期形成。

---

## 9.5 一个算子只有一个统一输出

当前：
```c
ControlModule_t
```
只提供：
```c
signal_t output_;
```
因此一个算子当前只有一个统一输出信号。一个输出可以连接到多个后级参数。

---

## 9.6 控制拓扑大小有限

当前：
```c
#define CONTROL_COMM_GRAPH_SIZE 100
```
因此 Graph 最大缓冲区为 100 Byte。复杂拓扑需要关注最终编码大小。

---

## 9.7 算子数量有限

当前：
```c
#define MAX_CONTROL_MODULES 30
```
单张控制拓扑最多创建 30 个算子。

---

## 9.8 算子内存池为 8 KB

当前：
```c
#define MODULE_MEM_POOL_SIZE (1024 * 8)
```
所有算子实例共同使用该内存池。新增较大的算子结构体时需要关注总内存占用。

---

## 9.9 外部参数数量有限

当前：
```c
#define CTRL_PARAM_MAX 32
```
输入参数注册表、输出参数注册表以及最终输出数组均基于该限制设计。

---

## 9.10 Mean Filter 最大窗口为 32

当前：
```c
#define MEANFILTER_WINDOW_MAX 32
```
超过该值时实际使用窗口会限制为 32。

---

## 9.11 非法配置主要通过 assert 处理

当前版本大量使用：
```c
assert()
```
处理：
- 参数未连接
- 参数类型错误；
- 模块不存在；
- 内存不足；
- 参数注册错误；
等情况。

因此在实际工程中应优先通过 Studio 和配置阶段保证控制拓扑正确。
当前版本并未针对所有非法配置提供完整的错误恢复能力。

---

## 9.12 无有效 Graph 无法正常建立控制关系

`ControlCore_Init()` 依赖有效 Graph 创建算子并完成连线。因此设备正式进入控制状态前必须已经具有有效控制拓扑。第一次使用时应先进入拓扑下载模式写入有效 Graph。

---

## 9.13 修改 Graph 后需要重新初始化

当前设计在：
```c
ControlCore_Init()
```
中建立全部算子和指针连接。正常控制过程中不会重新分析 Graph。因此更换控制拓扑后，需要重新启动设备或重新执行完整初始化流程。

---

## 9.14 Studio 当前通过正常关闭返回最终控制数据

当前 Studio 在图形界面退出后调用：
```python
control_graph.export_binary_manifest(...)
```
生成最终控制数据。因此使用 Host 调用 Studio 时，需要正常关闭 Studio 才能获得最新 Graph。

---

## 9.15 `.omni` 文件与 Graph 不可混用

`.omni`：
```text
用于保存 Studio 编辑工程
```

Graph：
```text
用于发送至 MCU
```
`.omni` 包含 UI 和工程信息，不能直接作为 MCU 控制数据使用。

---

## 9.16 输出索引需要保持约定

最终结果通过：
```c
ctrl_output_signal[]
```
提供。
如果应用程序按照固定索引使用输出，例如：
```c
ctrl_output_signal[0]
ctrl_output_signal[1]
```
则 Studio 中对应输出节点应按照预期完整连接。否则最终输出排列可能与应用层预期不一致。

---

# 10. 总结

从整体上看，OmniCtrl 的工作可以归纳为：
```text
          开发者
            │
      编写 / 选择算子
            │
            ↓
     omni_manifest.json
        ↙           ↘
       ↙             ↘
MCU 配置生成      OmniCtrl Studio
      │                 │
      ↓                 ↓
算子与参数注册      控制拓扑设计
      │                 │
      │                 ↓
      │               Graph
      │                 │
      └──────────┬──────┘
                 ↓
                MCU
                 │
          创建并连接算子
                 │
                 ↓
        周期执行控制计算
                 │
                 ↓
        ctrl_output_signal[]
                 │
                 ↓
             应用程序
```
OmniCtrl 将较复杂的拓扑设计、连接检查与执行顺序计算放在 Studio 中完成，而 MCU 端只需要根据已经生成的 Graph 建立算子及参数之间的关系，并在控制周期内依次完成计算。

对于普通使用者，如果已有算子能够满足需求，主要工作仍然只是：
```text
配置工程
   ↓
Studio 搭建控制拓扑
   ↓
下发 Graph
```
只有在已有控制能力无法满足需求时，才需要进一步编写新的算子或修改 OmniCtrl 本身。
